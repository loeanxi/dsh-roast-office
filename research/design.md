# dsh-吐槽办：Agent 行为审计员设计草案

Date: 2026-08-19
Status: research draft
Audience: dsh 插件设计与生态研究

## 1. 一句话定义

`dsh-吐槽办` 是一个观察 Agent 行为、识别可解释模式，并以可配置人格输出简短评论的 dsh 插件。

它的核心价值不是阻止 Agent 工作，而是把工具调用轨迹翻译成用户能快速理解的反馈：发生了什么、是否可能没有进展、下一步应该关注什么。

## 2. 背景与机会

Agent observability、轨迹评估和审计已经有较成熟的产品与研究方向。它们通常关注 tracing、成本、延迟、回放、合规和自动评测；`dsh-吐槽办` 关注同一类底层事实的轻量表达和交互体验。

dsh 已经提供了可复用的基础能力。`dsh-repeat-tool-reminder` 负责识别连续重复的同一工具调用并提醒模型；session 日志负责保存可回放事实；工具执行事件和 waterfall 扩展点负责让旁路插件观察调用。吐槽办应消费这些能力，不复制循环检测，也不修改 agent-loop。

## 3. 目标

- 在不改变工具执行结果的前提下，观察一次 Agent 回合中的工具调用、结果、失败和收尾状态。
- 把行为模式归纳为稳定、可测试的规则，而不是让模型自由发挥判断。
- 为每条规则提供简短的事实说明和可替换的文案风格。
- 让用户能区分事实、风险提示和玩笑，避免吐槽遮蔽错误或安全告警。
- 支持 headless、Web UI 和日志输出等不同宿主，核心包不依赖 UI。
- 让第一版在无额外模型调用、无 API key 的情况下运行。

## 4. 非目标

- 不阻止、重写、延迟或自动重试工具调用。
- 不替代权限、审批、超时、循环提醒或安全策略插件。
- 不尝试解释模型的私有思维过程，也不生成或展示“真实推理链”。
- 不用吐槽文案判断代码是否正确；正确性仍由测试、工具结果和用户审查决定。
- 不把每次工具调用都变成一条用户可见消息，避免增加上下文噪音。
- 不在第一版引入 LLM judge、远程服务、用户账号或跨用户排行榜。

## 5. 用户体验

### 5.1 默认输出

默认只在一个事件满足规则时输出一条短评，并带有机器可读的类型和严重程度。

```text
[吐槽办·循环] 连续 5 次调用 grep，参数没有变化。
建议：重新阅读最近一次结果，或换一个验证路径。
吐槽：你不是在搜索，你是在和文件系统培养感情。
```

### 5.2 任务结束摘要

回合结束时可选输出一条摘要，而不是逐条刷屏。

```text
[吐槽办·回合总结]
工具调用：14 次；失败：1 次；重复调用：5 次；测试：已观察到通过。
评价：改动已经收束，可以考虑提交。
成就：没有修改任务范围外的文件。
```

### 5.3 风格

文案风格是 provider 或纯配置选择，不属于规则检测器。建议内置：

| 风格 | 特征 |
| --- | --- |
| `neutral` | 只输出事实和建议，适合 CI、团队环境 |
| `gentle` | 轻微拟人化，不评价能力 |
| `roast` | 有梗但不攻击用户，不遮蔽事实 |
| `古风` | 实验性风格，适合演示 |

吐槽对象必须是行为，不是用户、团队、身份或能力。例如“这次调用没有改变参数”可以吐槽；“你很蠢”不可以。

## 6. 规则模型

规则检测器接收规范化的观察记录，返回零个或多个 `Finding`。检测器不直接拼接最终输出。

```text
type RoastSeverity = 'info' | 'notice' | 'warning'

interface Finding {
  readonly ruleId: string
  readonly severity: RoastSeverity
  readonly facts: Readonly<Record<string, string | number | boolean>>
  readonly recommendation?: string
  readonly dedupeKey: string
}
```

建议的首批规则：

| 规则 | 触发条件 | 处理建议 |
| --- | --- | --- |
| `repeat-call` | 同一 Agent 连续调用相同工具和规范化参数 | 重新阅读结果或改变路径 |
| `failed-retry` | 同一失败原因短时间内重复出现 | 检查错误原因，不要盲目重试 |
| `search-without-progress` | 多次搜索但查询或目标范围没有变化 | 收束搜索范围并形成假设 |
| `scope-drift` | 访问的文件集合明显偏离初始任务范围 | 询问是否需要扩大范围 |
| `unverified-change` | 已产生写入，但未观察到相应测试或验证动作 | 运行最小相关检查 |
| `clean-finish` | 改动集中、相关检查通过、没有待处理失败 | 可以提交或请求用户审查 |

第一版只实现事实可由事件直接证明的规则。`scope-drift` 和 `unverified-change` 需要定义明确的证据窗口，否则先作为研究项，不进入默认配置。

## 7. 插件边界与数据流

```text
工具调用 / 工具结果 / 回合生命周期
                 │
                 ▼
        观察记录归一化器
                 │
                 ▼
             规则检测器
                 │
                 ▼
       Finding 去重与严重度排序
                 │
          ┌──────┴──────┐
          ▼             ▼
     文案 provider     回合摘要器
          │             │
          └──────┬──────┘
                 ▼
          输出适配器 / 注释事件
```

插件应作为旁路观察者注册到已有工具和 Agent 生命周期扩展点。观察型 waterfall listener 必须调用 `next()`，不得通过不调用 `next()` 形成隐式阻断。

核心包只产生结构化 finding 和纯文本渲染结果。Web UI 若要增加徽章、颜色或时间线卡片，应由独立 client consumer 负责；核心包不能导入 UI 或 transport 类型。

## 8. 输出通道

第一版可支持三种互斥或组合的输出通道：

- `context`：向模型追加低频、短小的行为提醒，适合“可能卡住”的规则。
- `session-note`：写入可回放的插件来源记录，适合回合摘要和研究分析。
- `console`：输出给 headless 或开发者终端，适合演示和调试。

默认建议只启用 `console` 或宿主 UI 的旁路展示。若启用 `context`，必须限制频率和字符数，并确保注入内容可由 session 日志重建。

吐槽不应替换工具原始结果，也不应伪装成工具结果。严重程度为 `warning` 的安全或权限问题应由对应策略插件负责，吐槽办只能引用其公开结果。

## 9. 配置草案

```yaml
- id: roast-office
  name: '@deepseek-ai/dsh-roast-office'
  config:
    enabled: true
    style: roast
    channels: [console, session-note]
    rules:
      repeat-call: true
      failed-retry: true
      search-without-progress: true
      scope-drift: false
      unverified-change: false
      clean-finish: true
    maxFindingsPerTurn: 3
    summary: turn-end
```

配置解析必须在插件加载时拒绝未知风格、非法通道、负数阈值和未知规则名。规则阈值属于部署配置；协议字段、隐私保护和安全告警语义不应通过吐槽配置关闭。

## 10. 隐私与安全约束

- 默认不记录完整工具参数、文件内容、命令输出或 prompt，只保留规则所需的摘要字段。
- 文案 provider 不得收到密钥、环境变量、完整 diff 或未脱敏工具结果。
- 命令、路径和错误文本进入文案前需要经过现有的敏感信息脱敏策略；若没有可靠脱敏，应只输出计数和工具名。
- 吐槽文本必须标注来源，例如 `source: roast-office`，不能与 Agent 或工具的原始输出混淆。
- 规则状态默认按 Agent 和回合隔离，不能因为不同 subagent 共用工具注册表而互相污染。

## 11. 测试与验证

第一版应覆盖：

- 相同工具和相同规范化参数触发重复规则；参数键顺序不同仍视为相同。
- 不同 Agent 的计数互不影响；回合结束后状态正确清理。
- 未触发规则时没有额外输出。
- 同一个 finding 在同一回合不会重复渲染。
- 原始工具结果和错误结果保持不变。
- 各种 style 只改变文案，不改变 finding 的 ruleId、严重程度和事实字段。
- 敏感字段不会进入 finding 或渲染结果。
- keyless snapshot 覆盖一个完整的真实 runnable example，验证回合摘要和 console 输出。

## 12. 分阶段实现建议

### Phase 0：研究验证

只读取现有 session 和工具事件，统计可以稳定获得的事实字段，确认不同宿主能否显示旁路输出。

### Phase 1：纯规则与终端输出

实现 `repeat-call`、`failed-retry`、`clean-finish`，不注入模型上下文，不新增持久化事件，提供确定性的 console 输出和单元测试。

### Phase 2：回合摘要与 UI consumer

增加 session-note 或已有 telemetry 的结构化记录，并为 Web UI 提供独立摘要卡片。此阶段再决定是否需要新的 session event。

### Phase 3：可扩展规则与人格包

把规则和文案拆成注册表，允许生态插件添加规则或风格，例如“代码审查员”“项目经理”“古风县令”。注册规则必须声明输入字段、触发条件和隐私等级。

## 13. 关键未决问题

- 回合摘要应该写入 session log，还是只属于宿主展示状态？
- `context` 注入是否真的改善完成率，还是只增加 token 和干扰？
- dsh 是否已有足够稳定的“回合结束”事件可供摘要器消费？
- `scope-drift` 的初始范围由用户 prompt、首批文件，还是显式配置确定？
- 吐槽文案是否应该允许用户自定义模板，还是只允许选择内置风格？
- 规则 registry 是否值得独立成 Service Definition，还是第一版保持单包？
- Web UI 需要展示每条 finding 的证据，还是只展示摘要？

## 14. 成功标准

一个可用的研究原型应满足：

- 能在一次真实 dsh 任务中识别至少三种行为模式。
- 不改变工具结果、权限判断和 Agent 主循环行为。
- 相同输入轨迹产生稳定、可 snapshot 的结构化 finding。
- 用户能看懂每条评论对应的事实和建议，而不必相信吐槽本身。
- 关闭吐槽文案后，规则结果仍可被日志或测试消费。
- 通过一个小插件和配置行即可挂载，不需要修改 `agent-loop`。

## 15. 结论

`dsh-吐槽办` 最适合被设计成“结构化行为审计 + 人格化呈现”的旁路插件。它应建立在现有工具事件、session 可回放事实和 `dsh-repeat-tool-reminder` 等基础 guard 之上，把竞争重点放在可解释、低噪声和有趣的用户体验，而不是重新实现一套 observability 平台。
